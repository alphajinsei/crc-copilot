# CRC業務支援アプリ 要件定義・実装方針

本書は [requirement.md](../requirement.md)（ユーザーが記述した原文の要求）を踏まえ、
議論を通じて確定した要件と実装方針をまとめたものである。
実装の指針であると同時に、別セッションへ文脈を引き継ぐための資料でもある。

- 原文の要求 : `requirement.md`（ユーザーが管理。Claudeは勝手に編集しない）
- 確定した設計 : 本書（議論で決まったことを追記していく）

---

## 1. 何を作るか

治験業界で働く **CRC（治験コーディネーター）** の**相談役**となる業務アプリケーション。

CRCは日常業務で予期しない事象に直面する。「被験者が薬を飲み忘れた」「保管温度が逸脱した」
といった状況で、何をどの順で誰に対して行うべきかを判断しなければならない。

本アプリは、その相談に対して以下の2つを提供する。

1. **資料に基づく事実** — 関連文書を特定し、書かれている内容を出典とともに示す
2. **推奨アクション** — 各ステークホルダー（医師・上司・被験者・治験依頼者）へ
   次に取るべき行動を、優先順位をつけて提案する

本プロジェクトは **PoC**。実データは契約未締結・AI利用ガイドライン未整備のため入手できず、
サンプルデータを自作して開発を進める。

### 1.1 要件の変遷（2026-08-10）

当初は「ドキュメント検索の代行ツール」として設計していたが、
ユーザーが実際に求めていたのは「CRC業務の相談役」であることが判明し、要件を変更した。

| | 変更前 | 変更後 |
|---|---|---|
| 役割 | ドキュメント検索の代行 | CRC業務の相談役 |
| 入力 | 「〜はどう規定されているか」 | 「〜が起きた、どうすればよいか」 |
| 出力 | 事実の回答＋出典 | 事実の回答＋出典 **＋ 推奨アクション** |
| 前提 | 資料に答えが書いてある | **資料だけでは答えが出ないことがある** |

最後の行が本質的な変化である。「まず医師に報告し、その後モニターへ」という順序は
SOPに書かれていない。**アプリが業務常識に基づいて提案する**ことになる。

この変更により、アプリは「よきCRCであること」という役割を負う。
その定義を ⓪ 行動原則として明文化した（2章・5章参照）。

**変わらなかったもの**: 4層の絞り込みロジック、引用検証、全文投入方式。
これらは今回の変更と直交しており、そのまま土台として活きている。

## 2. データソースの階層構造

文書は「病院軸」と「治験軸」の2次元で分類される。
これに加え、アプリの振る舞いを定義する ⓪ を最上位に置く。

| 層 | 種別 | 作成者 | 存在数 | 上位文書 | 文書例 |
|---|---|---|---|---|---|
| ⓪ | **CRC行動原則** | CRCが所属する会社 | 1 | — | 行動原則、ステークホルダー対応指針 |
| ① | GCP | 国 | 1 | — | GCP省令 |
| ② | 病院文書 | 病院 | 病院数 | ① | hosp SOP、薬剤科SOP、検査科SOP、看護科SOP |
| ③ | 治験文書 | 製薬会社 | 治験数 | — | プロトコル（治験実施計画書）、治験薬概要書、同意説明文書、ラボマニュアル、コレクションフローチャート、治験薬取扱説明書 |
| ④ | 病院×治験文書 | CRC/現場 | 病院数 × 治験数 | ② と ③ | specific SOP（note to file、薬剤師ミーティング議事録） |

### 2.1 ⓪は①〜④と性質が根本的に異なる

**⓪は規則ではない。** この区別が本設計の要点である。

| | ①〜④ | ⓪ |
|---|---|---|
| 何を書いてあるか | **規則**（何が定められているか） | **行動原則**（どう振る舞うべきか） |
| 出典として引用するか | **する** | **しない** |
| 誰が作ったか | 国・病院・製薬会社 | CRCが所属する会社（自分たち） |
| 更新頻度 | 年10回程度 | UATフィードバックのたび |
| 用途 | 事実の回答の根拠 | 推奨アクションの組み立て |

**⓪を出典として引用しない**のが設計上の要点である。
⓪は「アプリがどう考えるか」の定義であって、CRCが原文にあたるべき根拠文書ではない。
ここを混ぜると「アプリの提案」が「規則に書いてあること」に見えてしまい、
要件の核心（出典のない断定をしない）が崩れる。

この制約は実装で担保する（4.5の `policy` 状態を参照）。

### 2.2 ⓪をシステムプロンプトに直書きしない理由

「よきCRCであること」の定義は**業務知識そのもの**である。
コードに埋め込むと、CRC側からレビューも修正もできない。

`data/00_policy/` に置くことで:

- CRC自身が編集でき、レビューでき、版管理できる
- 他の文書と同じ運用（年次改訂、UATフィードバックの反映）に乗せられる
- 組織ごとに異なる運用を反映できる

システムプロンプトには「⓪に書かれた行動原則に従え」という**指示だけ**を書き、
原則そのものは `data/` から読み込む。

### 文書階層と優先順位

```
        ⓪ CRC行動原則（規則ではない。アクションの拠り所）
        ─────────────────────────────────
        ① GCP（国）
             │
        ② 病院文書 ────┐
                        ├──→ ④ 病院×治験文書（最も具体的）
        ③ 治験文書 ────┘
```

- ② の上位文書は ①
- ④ の上位文書は ② と ③ の両方
- ③ は病院とは独立に存在するため、① との直接の上下関係は本PoCでは定義しない
- ⓪ は規則の階層の外にあり、①〜④と優先順位を争わない

**回答時の優先順位**: 具体的な文書ほど現場の実態に即している。
矛盾する記述があった場合は ④ > ②・③ > ① の順で優先し、
かつ「どの階層の文書が何と言っているか」を明示して矛盾自体をCRCに見せる。
黙って一方を採用しない。

## 3. 機能要件

### 3.1 入力

- **病院名** : 画面にボタン/選択肢として列挙。ユーザーは選ぶだけ（自由入力させない）
- **治験名** : 同上
- **質問文** : ここだけが自由入力

選択式にする理由は、ユーザビリティに加え、**指定内容を固定化して表記ゆれによる
文書特定の失敗を防ぐ**ため。病院名・治験名は内部的にIDで扱う。

### 3.2 文書の絞り込みルール

選択された病院ID `H` と治験ID `T` に対し、以下を参照対象とする。

| 層 | 条件 |
|---|---|
| ⓪ | 常に含める |
| ① | 常に含める |
| ② | `hospitalId == H` のもの |
| ③ | `trialId == T` のもの |
| ④ | `hospitalId == H` かつ `trialId == T` のもの |

このフィルタは**決定的なロジック**で行う。LLMに判断させない。
絞り込みの正しさは本アプリの根幹であり、確率的な処理を挟むべきではない。

### 3.3 出力：事実（資料に基づく回答）

1. **質問への回答**
2. **出典** — 文書名、および文書内の位置（見出し・条項番号）
3. **該当箇所の原文** — 逐語引用
4. **確信度の表明** — 以下の3状態を必ず返す
   - `grounded` : 明確な根拠あり
   - `ambiguous` : 根拠はあるが解釈・判断の余地がある
   - `no_evidence` : 根拠となる記述が見つからない

`ambiguous` / `no_evidence` の場合、断定的な回答をせず、その旨を誠実に伝える。
「出典はないが自信を持った回答」を返すことは本要件における明確な失敗である。

**確信度は事実の回答部分についてのもの**であり、推奨アクションの確からしさではない。
`no_evidence` でもアクションは提示しうる（後述）。

ハルシネーション対策の作り込みは**ベストエフォート**とする。
問題が顕在化した時点で設計を深掘りする方針で、まずは正常系の機能実現を優先する。

### 3.4 出力：推奨アクション（アプリによる提案）

CRCを取り巻く各ステークホルダーへ、次に取るべき行動を優先順位つきで提示する。

**構造は「優先度つきのフラットなリスト」とする。** ステークホルダーはタグとして各行に付ける。
グループ化や依存関係の構造化は行わない。CRCが実際に見るのは「次に何をするか」の1〜2件であり、
順序さえ正しければ依存関係は各アクションの説明文に書けば足りるため。

| フィールド | 内容 |
|---|---|
| `order` | 実行順序。1が最優先 |
| `stakeholder` | `doctor` / `supervisor` / `patient` / `sponsor` / `internal` |
| `action` | **誰に何を伝え、何を得るのか**を具体的に |
| `why` | なぜこの順序・この相手なのか |
| `timing` | 「本日中」「医師の判断確定後」など（任意） |
| `groundedIn` | 資料に根拠がある場合のみ documentPath（任意） |

**設計上の判断:**

- **`groundedIn` は任意。** アクションの多くは業務常識であり出典が付かない。
  付けられるものだけ付ける。無理に付けると出典全体の信頼性が薄まる
- **`why` は必須。** 順序の根拠を言語化させることで、CRCが状況に応じて調整でき、
  誤った順序も検出しやすくなる
- **`internal`** は記録作成など、対外的でないアクション用

このほか以下を返す。

- `situation` — 相談内容の理解を示す状況の要約。事実確認の質問では空
- `openQuestions` — 判断に必要だが不足している情報。**聞き返せることは相談役として重要**

### 3.5 事実と提案の分離（UI要件）

**画面上で明確に区切る。** これは要件の核心を守るための必須要件である。

```
┌─────────────────────────────────┐
│ 状況の理解                        │  ← situation
├─────────────────────────────────┤
│ 【資料に基づく事実】               │
│  確信度バッジ / 回答本文 / 出典     │
├═════════════════════════════════┤  ← 二重線で分離
│ 【推奨アクション】                 │
│  ⚠ これはアプリの提案です（常時表示）│
│  1. [医師] ... 2. [上司] ...      │
├─────────────────────────────────┤
│ 【確認が必要な事項】               │  ← openQuestions
└─────────────────────────────────┘
```

**「これはアプリの提案です」の注記は常時表示する。**
一度読めば分かることだが、常時出すことに意味がある。
CRCが上司や医師に「アプリがこう言っている」と伝えるとき、
それが規則なのか提案なのかを取り違えると実害が出るため。

## 4. 実装方針

### 4.1 技術スタック

**ブラウザUI**。UATを人間が実際に触るため。

方針として、**簡易な実装を優先する**。凝った実装でコンテキストと注意を消費し、
本来実現したい要件への集中が希釈されることを避ける。

- フレームワーク : Next.js（App Router）+ TypeScript
- スタイル : Tailwind CSS
- LLM : Anthropic API（`claude-sonnet-5` を既定）
- 状態管理・DB : なし。ファイルシステムから直接読む

サーバーサイドでファイルを読み、APIキーもサーバー側に保持する。

### 4.2 検索方式 — 全文投入（RAGを採用しない）

絞り込み後の文書を**全文そのままLLMのコンテキストに投入する**。
ベクトル検索によるRAGは採用しない。

**理由:**

1. **更新頻度** — 各文書は年10回ほど更新される。RAGでは更新のたびに再インデックスが
   必要になるが、全文投入ならファイルを置き換えるだけで済む
2. **チャンク境界による意味の欠落** — 治験SOPは「ただし〜の場合を除く」という
   条件分岐・例外条項が多い。例外が別チャンクに落ちると条件を無視した誤答になる
3. **出典精度** — 全文があればLLMは文書構造（章・節・項）を把握した上で
   正確な位置を示せる。チャンクのみだと文書内の位置情報が失われやすい
4. **検索漏れがない** — 質問文と文書の用語がずれても、絞り込み条件に合致する文書は
   必ず全て参照される

「原文の該当箇所を出す」要件について、RAGのほうが相性が良いということはない。
RAGの利点はチャンクがそのまま引用単位になる点のみで、上記1〜4の不利を上回らない。

**トークン量（サンプルデータでの実測、2026-08-10 ⓪追加後）**

全9通りの病院×治験の組み合わせについて、絞り込み後の文書量を計測した。

| 組み合わせ | 文書数 | 文字数 | 概算トークン |
|---|---|---|---|
| H001 × T001（最大） | 15 | 44,114 | 約24,500 |
| H002 × T001 | 14 | 41,625 | 約23,100 |
| H001 × T002 | 13 | 39,032 | 約21,700 |
| H003 × T003 | 11 | 36,713 | 約20,400 |
| （最小）H002 × T003 | 10 | 28,415 | 約15,800 |

**最大でも約24,500トークン**であり、コンテキストに余裕をもって収まる。
⓪の追加により全組み合わせで約9,000トークン増えたが、全文投入方式は維持できる。

将来データ量が増えて破綻する場合は、
「LLMに文書一覧（タイトル＋目次）を見せて必要な文書を選ばせる2段階方式」への
移行を検討する。ベクトル化はその次の選択肢。

### 4.3 文書の属性管理

**フォルダ階層を主軸とし、レジストリファイルで補完する。**

文書ファイル自体にラベルやフロントマターを埋め込むことは**しない**。
実運用では既存文書に固有のフォーマットが存在すると想定され、
本アプリ単独の都合でそのフォーマットに介入することは現実的でないため。

#### ディレクトリ構成

```
data/
├── 00_policy/                           ← ⓪ 常に参照される（規則ではない）
│   ├── crc-principles.md
│   └── stakeholder-map.md
│
├── 01_gcp/                              ← ① 常に参照される
│   └── gcp-ordinance.md
│
├── 02_hospital/
│   ├── H001_さくら総合病院/              ← ② {病院ID}_{表示名}
│   │   ├── hosp-sop.md
│   │   ├── pharmacy-sop.md
│   │   ├── laboratory-sop.md
│   │   └── nursing-sop.md
│   └── H002_みなと大学医学部附属病院/
│       └── ...
│
├── 03_trial/
│   ├── T001_ABC-201/                    ← ③ {治験ID}_{表示名}
│   │   ├── protocol.md
│   │   ├── investigators-brochure.md
│   │   ├── informed-consent.md
│   │   ├── lab-manual.md
│   │   └── drug-handling.md
│   └── T002_XYZ-305/
│       └── ...
│
└── 04_hospital_trial/
    ├── H001__T001/                      ← ④ {病院ID}__{治験ID}（アンダースコア2つ）
    │   ├── specific-sop.md
    │   ├── note-to-file.md
    │   └── pharmacist-meeting-minutes.md
    └── H002__T001/
        └── ...
```

**命名規約:**

- 病院ID : `H` + 3桁数字
- 治験ID : `T` + 3桁数字
- ② ③ のフォルダ : `{ID}_{表示名}` — アンダースコア1つ区切り
- ④ のフォルダ : `{病院ID}__{治験ID}` — **アンダースコア2つ**区切り。②③の区切りと衝突させない

#### レジストリ

`data/registry.json` に病院マスタ・治験マスタ・文書メタデータを保持する。
これはフォルダ構造から**スキャンして自動生成する**
（`npm run scan` → [scripts/scan.mjs](../scripts/scan.mjs)）。
人間はファイルを規約どおりのフォルダに置くだけでよく、
registry.json を手で編集することはない。

```json
{
  "generatedAt": "2026-08-09T00:00:00.000Z",
  "hospitals": [
    { "id": "H001", "name": "さくら総合病院" }
  ],
  "trials": [
    { "id": "T001", "name": "ABC-201試験" }
  ],
  "documents": [
    {
      "path": "02_hospital/H001_さくら総合病院/hosp-sop.md",
      "layer": 2,
      "hospitalId": "H001",
      "trialId": null,
      "title": "さくら総合病院 治験実施に関する標準業務手順書（Hospital SOP）",
      "docType": "hosp_sop"
    }
  ]
}
```

**スキャンスクリプトの挙動:**

- `title` は各Markdownの**先頭見出し（`# ...`）から自動抽出**する。
  文書側にメタデータを埋め込まない方針に沿い、既存文書に手を入れずに済む
- `docType` はファイル名から導出する（`hosp-sop.md` → `hosp_sop`）
- **命名規約への違反を検出したら、生成せずエラー終了する**
  - IDが `H\d{3}` / `T\d{3}` に合致しない
  - ②③のフォルダに表示名がない
  - ④のフォルダが `{病院ID}__{治験ID}` 形式でない
  - ④が参照する病院・治験が ②③ に存在しない（孤児フォルダ）
  - **⓪または①に文書が1件もない**（常に参照される層が空だと回答品質が崩れる）

規約違反を静かに通すと、絞り込みから文書が漏れて**誤答の原因になる**。
このスクリプトは単なる生成器ではなく、データ配置のバリデータでもある。

フォルダ階層だけに頼らずレジストリを噛ませる理由は、
将来「1つの文書を複数の治験で共有する」といった例外が生じたときに、
フォルダを動かさずレジストリ側で対応できる逃げ道を残すため。
また表示名の変更がフォルダ名変更を伴わずに済む。

### 4.4 処理フロー

```
[UI] 病院を選択 / 治験を選択 / 質問を入力
        │
        ▼
[API] POST /api/ask  { hospitalId, trialId, question }
        │
        ├─ 1. registry.json を読む
        ├─ 2. 絞り込みルール（3.2）で対象文書を決定  ※決定的ロジック
        ├─ 3. 対象文書の全文を読み込む
        ├─ 4. プロンプトを組み立ててLLMへ
        ├─ 5. 構造化された回答を受け取る
        ├─ 6. 引用文字列が原文に実在するか検証（後述）
        │
        ▼
[UI] 回答 + 確信度 + 出典 + 原文引用 + 参照した文書の一覧を表示
```

### 4.5 引用の検証

LLMが返した `quote`（原文引用）が、指定された文書の本文に**実際に存在するか**を
サーバー側で文字列照合して検証する。空白・改行・全角半角を正規化したうえで照合する。

引用の捏造は、ハルシネーションのなかで最も検出しやすく最も有害な失敗である。
LLMの自己申告に頼らない検証を1つ持っておく意味がある。

**照合結果は5状態に分類する**（[src/lib/verify.ts](../src/lib/verify.ts)）。

| 状態 | 意味 | UI |
|---|---|---|
| `exact` | 原文に連続した一節として存在する | 緑「原文と一致」 |
| `stitched` | 各文は原文にあるが、原文では連続していない | 黄「離れた箇所を連結」＋警告 |
| `not_found` | 原文に見つからない（捏造の疑い） | 赤「原文に該当なし」＋警告 |
| `no_document` | 参照対象外の文書を出典としている | 赤「参照外の文書」＋警告 |
| `policy` | **⓪行動原則を出典としている** | 赤「行動原則（規則ではない）」＋警告 |

`policy` は2.1の制約を機械的に担保するためのもの。
⓪を出典に挙げた場合、引用文が実在するかにかかわらず不可とする。
**プロンプトで禁じるだけでなく、検証側でも弾く。**
アプリの提案が規則に見えることは、要件の核心に反するため。

`stitched` を独立させたのは、実測で発生したため。LLMは離れた2文を `\n` で繋いで
1つの引用として返すことがある。**各文は実在するので捏造ではないが、
省略された部分に条件や例外が含まれている可能性がある**。捏造と同じ赤警告にすると
警告が形骸化するので、別扱いにして「原文を確認せよ」と促す。

判定は「各行が原文に存在し、かつ原文中で出現順序が保たれている」ことを条件とする。
順序が逆の場合は `stitched` とせず `not_found` に落とす。

**文書パスは照合の前に正規化する**（2026-11-22）。LLMは
`03_trial/T003_.../../../02_hospital/H003_.../pharmacy-sop.md` のように
`..` を含む相対指定でパスを返すことがあり、指す文書は参照対象なのに
文字列が一致せず `no_document` と誤判定された（実測）。`..`・`./`・`\` を解決してから
registry のパスと突き合わせる。他院の文書や参照範囲の外を指すパスは、正規化しても
一致しないので、これまでどおり `no_document` になる。

### 4.6 LLM出力のスキーマ

```ts
type Answer = {
  // ── 事実：資料に基づく回答 ──
  confidence: "grounded" | "ambiguous" | "no_evidence";
  answer: string;              // 回答本文。資料にないことを書かない
  caveat?: string;             // ambiguous / no_evidence のときの注意書き
  citations: Array<{
    documentPath: string;      // registry の path と一致すること（⓪は不可）
    location: string;          // 「第4章 3.2項」など文書内の位置
    quote: string;             // 原文の逐語引用
    relevance: string;         // なぜこれが根拠になるのかの一文
  }>;

  // ── 提案：アプリによる推奨アクション ──
  situation?: string;          // 状況の要約。事実確認の質問では空
  actions: Array<{
    order: number;             // 実行順序。1が最優先
    stakeholder: "doctor" | "supervisor" | "patient" | "sponsor" | "internal";
    action: string;            // 誰に何を伝え、何を得るのか
    why: string;               // なぜこの順序・この相手なのか
    timing?: string;           // 「医師の判断確定後」など
    groundedIn?: string[];     // 資料に根拠がある場合のみ documentPath
  }>;
  openQuestions?: string[];    // 判断に必要だが不足している情報
};
```

`no_evidence` の場合も `citations` は空配列で返させ、
「根拠がないこと」を明示的な状態として扱う。

**`no_evidence` でも `actions` は空とは限らない。**
「資料に定めはないが、原則としてはこう動くべき」という状況は頻繁にある。
これが検索代行と相談役の違いである。

`order` はLLMが飛ばしたり重複させたりしうるため、サーバー側で昇順にソートして
表示順を安定させる。

### 4.7 ストリーミング

ユーザーが実行時間を強く気にするため、回答は**ストリーミング表示**する。

処理の流れとイベントの順序は以下のとおり。

```
POST /api/ask  →  SSE (text/event-stream)
  1. meta          参照文書の一覧（LLMを待たずに即座に返す）
  2. answer_delta  回答本文の差分（複数回）
  3. done          検証済みの完全な回答（確信度・出典・引用検証の結果）
```

**`meta` を先に返すのが要点。** LLMの応答を待つ間、CRCは「何が参照されているか」を
確認できる。体感待ち時間が大きく変わる。

#### 構造化出力とストリーミングの両立

回答は `output_config.format` でJSONスキーマを強制している。このため
ストリーミングで届くのはJSON文字列であり、そのまま画面に出すと
`{"confidence":"gro...` のように見えてしまう。

そこで `JsonFieldExtractor`（[src/lib/anthropic.ts](../src/lib/anthropic.ts)）が
到着した断片から指定キーの値だけを逐次抜き出し、
JSONエスケープを解いて表示用テキストとして送る。
完成したJSONのパースは別途 `done` の直前に行うので、抽出側は表示専用である。

**注意点**: 断片の末尾が不完全なエスケープ列（`\` や `\u30d` など）で切れている場合、
その分の送出を保留し、次の断片と連結してから出す。保留した位置を送出済みに
含めないことが重要で、ここを誤ると**文字が欠落する**（実装時に実際に発生した）。
チャンク境界を1〜5000文字まで変えた単体テストで、
入力と出力が完全一致することを確認済み。

#### アクション追加に伴うストリーミングの変更（2026-08-10）

⓪とアクションの追加により、出力が `situation` → `answer` → `actions` →
`openQuestions` の順に生成されるようになった。

**`answer` だけを追うと、出力の後半で画面が止まって見える。**
実測では本文499字に対し総出力1,600字であり、**7割近くが `answer` の後に生成される**。
82秒の応答のうち大半でカーソルが点滅するだけになっていた。

そこで `AnswerStreamFormatter` が表示用テキストを段階的に組み立てる。

```
【状況の理解】
（situation の内容）

【資料に基づく事実】
（answer の内容）

推奨アクションを作成しています…    ← actions 生成中の進捗表示
```

`done` で構造化された回答が届いた時点で、UIはこの暫定表示を破棄し、
セクション分けされた本表示に切り替える。

#### 実測値

| 項目 | 実測 |
|---|---|
| 最初の `meta` 到達 | 1秒未満 |
| 回答完了まで | 20〜85秒 |

⓪とアクションの追加により、変更前（7〜35秒）から**倍以上に伸びた**。
相談型の質問（アクション5件＋確認事項6件）で約82秒。
これは出力トークン量の増加によるもので、避けられない。
ストリーミング表示の改善で体感を緩和しているが、
**UATで「遅い」というフィードバックが出た場合は対策を検討する**（7章参照）。

**意図的に仕込むテストケース:**

回答品質を検証できるよう、以下の状況をサンプルデータに埋め込む。

| ケース | 意図 |
|---|---|
| ④ が ② の規定を上書きしている箇所 | 階層の優先順位が正しく働くか |
| ②と③で手順が食い違う箇所 | 矛盾を検出して両論併記できるか |
| どの文書にも書かれていない論点 | `no_evidence` を正しく返せるか |
| 条件付き・例外つきの規定 | `ambiguous` を返して判断を丸投げしないか |
| 病院ごとに異なる規定（同じ論点） | 絞り込みが効いているか（他病院の規定を混ぜないか） |

最後のケースは絞り込みロジックの検証に特に有用である。
H001とH002で異なる規定を置いておけば、誤って両方を参照した場合すぐ露見する。

### 5.1.1 ⓪ CRC行動原則（2026-08-10 追加）

| ファイル | 内容 |
|---|---|
| `crc-principles.md` | CRCの権限範囲、行動原則5つ、イレギュラー対応の6ステップ、適用例4件 |
| `stakeholder-map.md` | 5者それぞれの権限・連絡原則・留意点、状況別の順序判断表 |

**行動原則5つ**（優先度順）

1. 被験者の安全が最優先
2. **判断は権限のある者が行う** — CRCは判断せず、判断できる人に繋ぐ
3. 記録は即時に、事実のみを
4. 迷ったら報告する
5. 一次情報にあたる

原則2を上位に置いたのは、CRC業務の誤りの多くが
「権限外の判断をしてしまう」ことに起因すると考えたため。

**連絡順序の基本形**: 医師 → 上司 → 被験者 → 治験依頼者

| 順 | 相手 | なぜこの位置か |
|---|---|---|
| 1 | 医師 | 医学的判断の権限を持つ。判断が出ないと他に伝える内容が確定しない |
| 2 | 上司 | 業務品質と体制に責任を負う。早期把握で組織対応が可能になる |
| 3 | 被験者 | 医師の判断前に説明すると、覆ったときに混乱・不信を招く |
| 4 | 治験依頼者 | 施設内の事実確認前の報告はかえって混乱を生む |

**文書設計上の工夫:**

- **「なぜこの順序か」を必ず書いた。** 順序だけだと状況が変わったとき機械的に当てはめて誤る。
  理由が書いてあればLLMが組み替えられる
- **例外を先回りして書いた。** 重篤な有害事象は報告期限が順序に優先する。
  原則だけだと期限のある事象で誤った順序を提案する
- **適用例4件のうち1件（来院なし）は、あえて被験者を最初に置いた。**
  原則の順序が絶対でないことを示すため。事実確認が先行しないと医師に報告する内容が確定しない
- **「責めない」を明記した。** 責めると次から申告しなくなり、
  **かえって安全性が損なわれる**という理由まで書いた

### 5.3 テストケースの実行結果（2026-08-09）

5.2 の仕込みを実際に流した結果。すべて実APIでの実測。

| ケース | 組み合わせ | 結果 | 判定 |
|---|---|---|---|
| どこにも書かれていない論点 | H001×T001 | `no_evidence` / 出典0件 / 6.9秒 | ✅ 正しく「ない」と答え、確認先まで案内 |
| 夜間休日のSAE報告（病院ごとに異なる） | H002×T001 | `grounded` / 出典5件 / 16.9秒 | ✅ H002の12時間を採用。H001の規定は混入せず |
| ④が②の制約を解決（超低温保管なし） | H003×T003 | `grounded` / 出典4件 / 16.7秒 | ✅ ④の議事録の「フリーザー貸与」に到達 |
| ②と③の矛盾（絶食8h vs 10h） | H002×T001 | `grounded` / 出典7件 / 19.1秒 | ✅ 両論を明示し、優先規定を根拠づけて10hを採用 |
| ④が存在しない組み合わせ | H002×T003 | `ambiguous` / 出典7件 / 35.0秒 | ✅ ④の不在を明言し、④を捏造しない |

**特筆すべき点:**

- **絞り込みが実際に機能している。** 夜間SAEは3病院で結論が異なるが、
  他院の規定が混入した形跡はなかった
- **④を見ないと誤答するケースを正しく突破した。** H003×T003 の超低温保管は、
  ②だけ見ると「設備がないので実施不可」と答えてしまう。④の議事録まで
  読んで初めて正解（治験依頼者がフリーザーを貸与）に辿り着く
- **④がない組み合わせで `ambiguous` を返した。** 存在しない④を捏造せず、
  「④で定めるべき事項が未定である」と正しく指摘した。これは想定以上の挙動
- **引用検証が実際に働いた。** 27件の引用のうち1件が不一致として検出された。
  内容を確認したところ捏造ではなく「離れた2文の連結」であり、
  これを機に `stitched` 状態を新設した（4.5参照）

### 5.4 相談役への転換後の動作確認（2026-08-10）

要件変更後、要求仕様に挙げられた代表例で確認した。

**質問**: H001 × T001 /「被験者から電話があり、治験薬を3日分飲み忘れたと言っています。どうすればよいですか？」

| 項目 | 結果 |
|---|---|
| 確信度 | `ambiguous` |
| 出典 | 2件（いずれも `exact`） |
| アクション | 5件 |
| 確認事項 | 6件 |
| 応答時間 | 82秒 |

**確認できた挙動:**

- **事実と提案が分離された。** 回答本文は「単日の飲み忘れの規定はあるが、
  複数日の規定は資料にない」と述べるにとどまり、
  順序の助言はアクション側に置かれた
- **⓪の適用例が効いた。** アクションの順序が
  「被験者（事実確認）→ 医師 → 上司 → 被験者（案内）→ 治験依頼者」となり、
  **原則の基本形（医師が最初）を状況に応じて組み替えている**。
  ⓪の適用例4（来院なし）で「事実確認が先行する場合がある」と示した効果と考えられる
- **`groundedIn` が正直に使われた。** 5件中1件（服薬率80%の報告義務）にのみ
  資料の根拠が付き、残り4件は空だった
- **`openQuestions` が機能した。** 「何日分か」「気づいた時点で服用したか」など
  6件を挙げ、情報不足のまま断定しなかった
- **理由が具体的だった。** 「医師の判断前に伝えると、判断が異なった場合に
  被験者の不信を招き、過量服用のリスクもある」と、⓪に書いた理由が反映された

**この実行で判明した課題:** ストリーミング表示が `answer` で止まり、
出力の7割を占める `actions` の生成中に画面が動かなかった。
`AnswerStreamFormatter` を追加して対応した（4.7参照）。

## 6. 進め方

```
サンプルデータ作成 → 業務アプリ開発 → UAT（人間が実施） → フィードバック → 改修
                                          ↑                              │
                                          └──────────────────────────────┘
```

このループを複数回まわしてアプリを洗練させる。
UATは人間が実施する。Claudeは実装とフィードバックの反映を担う。

### 6.1 起動方法

```sh
npm install
npm run scan      # data/ から registry.json を生成
npm run dev       # http://localhost:3000
```

`.env.local` に `ANTHROPIC_API_KEY` を設定する（`.env.local.example` を参照）。
**キーが未設定の場合はモックモードで動作する** — 固定応答を返し、APIを消費しない。
UI調整やデモの際はキーを外しておけばよい。画面上部にモックモードである旨が表示される。

### 6.2 API利用コストの目安

実測値に基づく概算（Sonnet、入力 $3 / 出力 $15 per 1M tokens）。

| 項目 | 1質問あたり |
|---|---|
| 入力 約24,500トークン | 約 $0.074 |
| 出力 約900トークン | 約 $0.014 |
| **合計** | **約 $0.09（約13円）** |

⓪の追加で入力が約9,000トークン増えたが、
1質問あたりのコストは約12円 → 約13円と小幅な増加にとどまる。

同じ病院×治験で連続質問する場合、プロンプトキャッシュにより2回目以降は
入力コストが約1/10になる（文書部分に `cache_control` を設定済み）。
UATで100問試しても1,000円台に収まる見込み。

## 7. 未決事項 / 今後の論点

| 論点 | 現状 | 検討タイミング |
|---|---|---|
| **アクションの品質検証** | UATでの人間の判断が唯一の手段 | UAT実施時 |
| **回答時間** | **20〜85秒**。⓪追加で倍増した | **遅いという指摘が出たら（可能性が高い）** |
| ハルシネーション対策の深掘り | ベストエフォート（引用検証は実装済み） | 問題が顕在化したら |
| 会話の継続（追加質問） | 単発Q&Aのみ。**相談役としては対話が自然** | UATフィードバック後 |
| 回答履歴の保存 | なし | UATフィードバック後 |
| 出典から原文へのジャンプ | パスと位置の表示のみ | UATフィードバック後 |
| ⓪の組織別カスタマイズ | 単一の原則のみ | 複数組織で使う段階になったら |
| PDF対応 | Markdownのみ | 本番移行時 |
| データ量増加時の対策 | 全文投入で足りる（実測24.5k tokens） | トークン超過が起きたら |
| 認証・権限管理 | なし（PoC） | 本番移行時 |
| ①GCPと③治験文書の上下関係 | 未定義 | 必要が生じたら |

### 7.1 回答時間について

⓪とアクションの追加により、応答時間が **7〜35秒 → 20〜85秒** に伸びた。
出力トークン量の増加が原因であり、現状の設計では避けられない。

対策の選択肢（未実施）:

| 案 | 内容 | 副作用 |
|---|---|---|
| A | アクション件数の上限を設ける（例: 5件） | 必要な行動が落ちる可能性 |
| B | `situation` を省略する | 状況理解の確認ができなくなる |
| C | 質問の性質で⓪の投入を出し分ける | 判定を誤ると劣化する |
| D | 事実の回答を先に返し、アクションを別リクエストにする | 実装が複雑。合計時間は変わらない |

**UATで実際に「遅い」と感じられるかを確認してから選ぶ。**
参照文書リストが1秒未満で出るため、体感は実測値ほど悪くない可能性がある。

### 7.2 アクションの品質検証について

事実の回答は出典で機械的に検証できるが、
**「この順序が適切か」は業務知識のある人間にしか判断できない。**

UATでの評価が唯一の手段となる。
不適切な順序が見つかった場合、修正すべきは⓪の行動原則であり、
コードやプロンプトではない（2.2の設計判断による）。
